## 1. 总体结论

在已确定的产品范围内（`open` 亮牌模式），V1.0 第 3～9 节的可执行规则已经全部落地，AI 亮牌主链路按 A→B→C→D 运行，且行为与文档公式基本一致。

按产品决定，`hidden` 暗亮模式暂不实现；规则 `game` 段的读秒/自动亮仍以开始页设置为准。这两项属于明确的产品化选择，不是引擎公式缺陷。

## 3. 发现的问题

### 3.1 [已修复] 亮牌读秒结束未提交当前选择

- **规范要求**：§3.3 “`lightSeconds ∈ [5,60]` 时，倒计时结束自动提交当前选择（通常为空）”。
- **修复前行为**：`beginLighting` 的读秒定时器在归零时直接调用 `finishLighting()`；如果南家尚未点击“亮牌”，`submissions.S` 为空，玩家已经弹起的牌不会被提交。
- **修复**：在 `src/store/game.ts` 增加 `autoSubmitHumanLightOnTimeout()`，归零时先提交 `humanLightSelection`，再进入揭晓。
- **测试**：`src/__tests__/store.test.ts` 新增“亮牌读秒结束自动提交当前选择”，使用种子 7（南家持 ♠Q）验证超时后 `submissions.S` 包含 ♠Q、`litBy[PIG] === 'S'`。

### 3.2 [产品决定不实现] `hidden` 亮牌信息模式

- **规范要求**：§3.1、§9.4。`hidden` 模式下亮牌阶段只能使用“已提交亮牌数量”，不得使用牌种。
- **当前行为**：
  - `lightRuleConfig` 能校验 `game.light_info_mode='hidden'`，但 `store/game.ts` 从未读取该字段；
  - `publiclyLitCards()` 在亮牌阶段始终把 `submissions[pos]` 合并为公开牌；
  - `Table.vue` 的 `visibleLit()` 在亮牌阶段直接展示 `submissions[pos]`；
  - `LightDecisionInput.litCount` 被传入但引擎未使用。
- **行为影响**：
  - 对 AI 自身决策影响很小：关键牌全局唯一，玩家只能亮自己持有的牌，因此“别人已亮的牌”不会出现在自己的 `heldKeys` 中；
  - 对真人信息边界影响明确：`hidden` 模式应隐藏他人已提交牌种，当前会公开。
- **说明**：README 已明确当前产品选择“提交后立即公开”，覆盖 SRS 的暗亮展示限制。产品已决定现阶段不实现 `hidden`，因此这是**有意的产品偏差**，不是引擎公式错误。
- **后续**：若未来需要暗亮，应同时改三处：规则读取、`publiclyLitCards()`、`Table.vue` 展示；并让引擎只接收 `litCount`。

### 3.3 [已修复] 模块 C 可在没有估算器时开启

- **规范要求**：§7.1 “在估算器未实现前，禁止开启，避免用拍脑袋概率放大波动”。
- **这个问题的含义**：模块 C 是给亮牌概率再乘一个“满贯概率修正”`F_slam`。它需要外部先算出本队/对方达成满贯或全红的概率；当前项目没有这个估算器，所以 `moduleC()` 在 `!slam` 时会返回 1。也就是说，管理员即使把 `module_c.enabled` 改成 `true`，规则看起来启用了，实际概率完全不变，是一个“静默无效”的开关。
- **修复**：`normalizeLightRule()` 现在直接拒绝 `module_c.enabled=true`，错误信息说明“尚未接入满贯概率估算器”。规则面板导入或应用此类配置时会立即报错，而不是静默忽略。
- **测试**：`src/__tests__/lightRules.test.ts` 新增“模块 C 在未接入满贯概率估算器前禁止启用”。

### 3.4 [配置源偏差] 规则 `game` 段不是读秒/自动亮的唯一参数源

- **规范要求**：§10 “本文件第 10 节配置为唯一参数源”。
- **当前行为**：
  - `store/game.ts` 使用开始页 `GameConfig` 的 `lightSeconds`、`playSeconds`、`autoLightLastOne`；
  - 规则 JSON 的 `game.light_seconds`、`game.play_seconds`、`game.auto_light_last_one` 只参与导入/导出，不驱动实际行为；
  - README 第 54 行已说明“实际读秒与第四张自动亮仍以开始页设置为准”。
- **结论**：实现与产品现状一致，但与 V1.0 §10 的“唯一参数源”表述冲突。建议修订规范，或把 store 改为优先读取激活规则并保留开始页作为覆盖项。

### 3.5 [规范自身] `x=-0.60` 处分支概率不连续

- **规范表述**：§5.2 称强度插值“保证阈值处连续”；§14 再次强调“所有分支概率在阈值处连续”。
- **实际问题**：
  - 在 `x=-0.60` 时，`desperate` 的 `m=0`，概率等于常规值；
  - 在 `x=-0.599` 时，`gamble` 的 `g≈0.997`，概率几乎直接跳到绝境目标值；
  - 因此 `x=-0.60` 两侧存在明显跳变，尤其是猪/♥A/变压器。
- **实现状态**：`branchStrength` 严格按文档公式实现，**不是实现 bug**，而是规范公式自身的问题。
- **建议**：把 `gamble` 的强度改为从 `x=-0.60` 处从 0 开始（例如 `g=clamp((-x-0.60)/0.30,0,1)`），或把 `desperate` 的目标值在 `m=0` 处与 `gamble` 的目标值对齐。修订前不要修改实现，否则会偏离冻结规则。

### 3.6 [已修复] 猪 3 张“常规不考虑亮”改为硬否决

- **规范表述**：§6.2/§6.7 “猪 3 张时 `F_cnt∈[0.55,0.60]`，常规不考虑亮”。
- **修复前行为**：`moduleB` 只做 `clamp(cnt,0.55,0.6)`，候选构建阶段没有对“猪 3 张 + normal”做硬过滤；管理员自定义较低阈值或较高基准概率时仍可能亮出。
- **修复**：`decideLights` 的候选过滤新增 `flag==='normal' && 黑桃张数===3 → 否决猪`。绝境/搏杀分支仍按规则文档保留赌博性亮猪。
- **测试**：`src/__tests__/lightRules.test.ts` 新增“猪门恰好 3 张时常规分支硬性不推荐亮猪，绝境分支仍可赌博性亮猪”。

### 3.7 [文档示例] `F_hA` 的 “A + 2 大 + 3 小” 与公式口径不完全一致

- **规范 §6.3 示例**：`L_h=6`、`k_top,h=1.5`、`s_low,h=3`、`F_hA≈0.839`。
- **按定义**：`k_top,h=#A+0.5#K+0.5#Q`。若“2 大”指 K+Q，则 `k_top,h=1+0.5+0.5=2.0`，代入公式得到约 0.917，而不是 0.839；要得到 0.839，需要 `k_top,h=1.5`。
- **实现状态**：`moduleB('hA')` 按公式计算，不按示例硬编码。
- **建议**：修订示例中的牌型描述或 `k_top` 数值，避免审计时被误认为实现偏差。

### 3.8 [低优先级] `litCount` 未被使用

- `LightDecisionInput.litCount` 已从 `store` 传入，但 `decideLights` 没有读取。
- 在 `open` 模式下没有影响；在 `hidden` 模式下它是唯一允许使用的亮牌信息，应在实现 `hidden` 时接入（例如用于调试、上限或未来策略）。
- 当前可保留字段，但应在类型注释中标注“预留给 hidden 模式”。
